## 后端（PHP/Webman）

### 异常分层与类型定义
- `server/plugin/xbCode/exception/business/ExceptionBase.php`：所有业务异常的抽象基类，继承 PHP Exception，提供 $code、$eventName、$option 等字段以及 getEventData() 方法。
- 具体业务异常按 HTTP 语义细分，均位于 `plugin/xbCode/exception/business/` 下：
  - `ExceptionUnauthorized`（401）— 未登录 / Token 失效
  - `ExceptionBadRequest`（400）— 参数校验失败
  - `ExceptionNotFound`（404）— 资源不存在
  - `ExceptionForbidden`（403）— 权限不足
  - `ExceptionMethodNotAllowed`（405）、`ExceptionBadGateway`（502）、`ExceptionServiceUnavailable`（503）、`ExceptionInternalServerError`（500）、`ExceptionRedirect` 等
- 部分插件 API 仍直接 throw new Exception('...') 或 RuntimeException，尚未完全迁移到自定义异常类。

### 全局异常处理器
- `server/config/exception.php` 将空键映射到 support\exception\Handler::class；实际项目通过 `plugin/xbCode/exception/Handler.php` 覆盖 Webman 默认 ExceptionHandler。
- `xbCode/exception/Handler::render()` 核心逻辑：
  - 优先判断 hg\apidoc\exception\HttpException，返回 JSON {code, message}。
  - 对 support\exception\BusinessException 和 plugin\xbCode\exception\business\ExceptionBase 子类，根据请求是否为 AJAX/JSON 决定走 renderJson 还是 renderView。
  - 普通 Exception 在 JSON 请求下也走 JSON 渲染。
  - 非 JSON 请求统一渲染 `/plugin/xbCode/exception/view.html` 视图，debug 模式下附带 file/line/trace。
- `renderJson` 输出结构：{message, code, debugData?, eventData?}，其中 eventData 来自异常的 getEventData()，debugData 仅在 DebugApi::status() 开启时包含文件、行号、堆栈。

### 事件机制
- 每个业务异常可携带 eventName + option，由 Handler 统一打包为 eventData 随响应返回，前端据此触发对应 UI 行为（如踢出登录、提示弹窗）。

## 前端（Vue3/Axios）

### Axios 拦截器链
- `frontend/src/utils/request/index.ts` 组装三个拦截器：
  - `requestInterceptors`：请求前注入 token、基础 URL 等。
  - `responseInterceptors`：检查后端返回的 data.status !== 0，视为业务错误，广播 business-error 事件并 reject。
  - `errorInterceptors`：捕获网络层错误，按 HTTP 状态码广播不同事件：
    - 403 → forbidden
    - 301/302 → redirect-permanent / redirect-temporary（携带 location）
    - 其他 → http-error
- 所有事件通过 appEventBus（基于 mitt）以强类型 RequestEventDetail 广播，包含 type/message/status/url/response。

### 调用方消费模式
- Store（如 `stores/user.ts`）中大量使用 try/catch 包裹异步调用，catch 后通常记录日志或忽略，依赖上层组件或全局监听处理用户可见的错误提示。
- 确认弹窗等 UI 组件内部也有 .catch(() => {}) 静默处理取消操作。

## 架构约定与开发规则

1. 后端抛异常：新增业务错误应创建 plugin/xbCode/exception/business/ 下的新异常类，设置正确的 $code 与可选的 eventName/option，避免直接 throw new Exception('...')。
2. HTTP 语义对齐：400/401/403/404/405/500/502/503 等已有对应异常类，直接使用即可。
3. JSON 优先：API 请求均为 AJAX/JSON，Handler 会统一返回 {message, code, ...} 格式，前端无需解析 HTML 错误页。
4. 前端统一入口：所有 axios 请求必须经过封装后的 request 实例，不要绕过拦截器；业务错误通过 business-error 事件集中处理。
5. 事件驱动 UI：利用 appEventBus 广播的错误事件在布局层（如 TopBar 通知面板）统一展示，避免在各页面重复 try/catch。
6. 调试开关：生产环境关闭 DebugApi 后，异常响应不再泄露堆栈信息，仅保留 message/code/eventData。
